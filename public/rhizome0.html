Technical Architecture Proposal

rNet × Rhizome

Budget dMachine + Maker MVP — the smallest system that runs the full loop: QFX upload → living budget app → "describe an app, get it."

status proposal-draft v2 aligned to spec v0.4 stack Bun · Hono · Zod · Pi · R2

00Objective & success criteria

Raw bank export → origin artifact → ingestion (skill-guided, verified, dry-run gated) → transaction Vibe → push categorization → budget dMachine renders → user edits persist → monthly pull keeps the Vibe alive.
  1. A stranger with a Chase QFX file gets a working, personalized budget app in under three minutes, every object carrying conformant provenance.
  2. A stranger with a weird credit-union CSV gets the same result via the generated-parser path.
  3. the unlock
    A stranger describes an app — "budget app, but for my freelance invoices" — and the Maker generates a working dMachine against their Vibe, sandboxed and scope-limited.

The Maker is the same agent harness pointed the other direction: Pi generates parsers on the write edge, dMachines on the read edge. One runtime, two factories.

01Repo topology

Two repositories with a hard ownership boundary that mirrors the protocol/product split.

rnet/ open · the protocol

Apache-2.0 or MIT. The rNet Foundation's eventual home. Contains nothing Rhizome needs to keep: the spec, JSON Schemas (source of truth), generated @rnet/types, and the conformance suite.

rhizome/ product

License TBD (BUSL or closed). Server, ingestion runtime, skill corpus, dMachine SDK, budget app, the Maker. Depends on rnet packages; never vice versa.

rhizome ─────▶ rnet  ·  the dependency arrow points one way. If rnet ever needs something from rhizome, it's either (a) actually protocol — move it — or (b) a design error.

rnet/ layout

rnet/
├── spec/rnet-spec.md          # the spec (v0.4+), canonical prose
├── schemas/0.4/               # THE PROTOCOL — JSON Schema, source of truth
│   ├── media-element.json · media-object.json · origin-artifact.json
│   ├── vibe.json · ingest-record.json · grant.json  # subjects + scopes (spec §3)
│   └── types/  transaction.json · track.json · document.json
├── packages/
│   ├── types/                 # @rnet/types — TS + Zod, GENERATED from schemas/
│   └── conformance/           # @rnet/conformance — runnable vs ANY store
└── README.md                  # second-implementer framing

Schemas are the source of truth; Zod is derived. A Python implementer ignores packages/ and consumes schemas/ with Pydantic — that's the point. The conformance suite tests both edges: write-edge (source immutability, origins fetchable, export round-trip lossless) and read-edge (spec §3: write:user can't corrupt source; read can't see origins; revoked grants fail closed; share can't self-escalate).

RuntimeBunFast hashing (content-addressing is the hot path), zero-config TS, one binary. Standards-only code in packages keeps Node portability.

MakerSame Pi harness + templates + sandboxThe spec is the prompt: generation sees @rnet/types + SDK, never Vibe data — closing the injection channel architecturally. Generated apps meet data only at runtime, inside the sandbox.

03The skill corpus — the accumulating asset

Skills live in apps/ingest/skills/, one directory each. Three required files; the format is ours, not Pi's — the corpus must survive harness mortality.

FileRole
SKILL.mdFormat knowledge: field mapping to the type vocabulary, edge cases (Chase QFX quirks, date formats, sign conventions).
VERIFY.mdRequired. Invariants the runtime executes post-parse: object count = record count, Σ amounts = statement total, required fields present, fitid unique.
BOUNDARIES.mdRequired. Permitted paths only — user-initiated exports, sanctioned APIs, no credentialed scraping. The compliance posture, versioned.
scripts/Optional deterministic parsers → method: "compiled", the top rung.

The determinism ladder: compiled script → reproducible: true. Agent on a known format → method: "skill". Novel format → generated parser → parser_hash recorded, VERIFY gauntlet, forced dry-run review → approval seeds parser_cache keyed by format signature.

The cache converts the long tail into compiled capability over time — every weird format any user brings becomes permanent, zero-marginal-cost coverage. The corpus and cache are the defensible asset, not the product: the product is the §00 loop. The asset accretes as exhaust from users running it.

04End-to-end flow

 1. UI: drag in chase_export.qfx
 2. POST /origins                    → rnet://origin/sha256:3c4f…
 3. POST /vibes                      → "My Spending"
 4. POST /vibes/{id}/pull {dry_run}  → Pi job: ofx skill, compiled path
 5. runtime runs VERIFY.md          → 214 candidates · zero elements
                                       (fields are facts; elements are content)
 6. review: "totals reconcile ✓"     → user confirms → commit
 7. POST /vibes/{id}/push            → categorize · essence · metering rows
 8. budget-app granted               → [read, write:user, push]
 9. user recategorizes               → PATCH /objects/{id}/user (If-Match)
                                       sticky across re-pushes forever
10. monthly: new export → 2,4,6,7    → the Vibe stays alive

Novel-format variant of step 4: no matching skill or cache → agent generates parser → hash + full gauntlet → dry-run review is required, not optional → approval seeds the cache.

06Decisions this proposal makes — veto points

  1. SQLite over Postgres for v0 Single-node honesty; Drizzle keeps the exit. Litestream → R2 continuously: DB and blobs share one durability story.
  2. R2 for blobs from M1, filesystem for dev only Durability by construction over DIY sync jobs; velocity means never building the backup path.
  3. Conformance suite lives in rnet, runs in rhizome CI The open repo holds the certification asset; the product is its first subject.
  4. Transactions ship with zero elements Fields are facts; elements are content. First element-exercising demo (receipt PDFs + decomposition) is post-M7.
  5. Skill files are Rhizome-private at launch Conformance rules are public in the spec; the corpus is the moat. Revisit if ecosystem pressure warrants promotion (spec punt #6).
  6. Phone-first auth, passkey upgrade OTP for signup/recovery; passkey becomes the login factor. Identity stays a spec punt — server implementation, invisible to protocol.
  7. Metering from M3, enforcement later Record every token from the first push; budgets and developer-pays billing are post-MVP. Metering lives in the dMachine SDK, not the protocol.
  8. Maker generates against schemas, never data The injection channel closes architecturally; sandbox + server-enforced grants contain whatever generation gets wrong anyway. Every generated app is code-hashed — the fork graph starts at M6 metadata.

07Deferred, deliberately

Federation, E2EE, DIDs, inter-store sharing (spec punts 1–3). Music/track ingestion and capability negotiation (MusicKit auth — post-M7). The dMachine store as a surface — though its substrate ships early: M6 registers every generated app code-hashed with fork provenance, so the store is a UI over data that already exists, populated autogenously by Maker usage. Payments settlement. The rNet Foundation — it needs a second implementer to govern; the conformance suite is its dowry, waiting.
